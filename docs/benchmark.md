## 1. 정렬 알고리즘 비교 (보너스)

```bash
python scripts/benchmark_sort.py                 # 100 / 1,000 / 5,000 / 20,000
python scripts/benchmark_sort.py 100 1000 50000  # 크기 지정
```

### 이론적 특성

| 알고리즘 | 평균 | 최악 | 추가 공간 | 안정 |
|---|---|---|---|---|
| merge | O(n log n) | O(n log n) | O(n) | ✅ |
| quick | O(n log n) | O(n²) | O(log n) | ❌ |
| heap | O(n log n) | O(n log n) | O(1) | ❌ |
| insertion | O(n²) | O(n²) | O(1) | ✅ |

Python 3.13.16 / linux

### 해석

- **무작위 입력**: 병합·퀵이 비슷하고 힙이 약 1.5배 느립니다. 힙 정렬은 배열을 멀리 건너뛰며 비교·교환해 상수 비용이 큽니다.
- **이미 정렬된 입력**: 삽입 정렬이 O(n)으로 압도적으로 빠릅니다(2만 개 3.8ms). 커밋은 대부분 시간순으로 쌓이므로 `--sort-by=date`에서 실제로 유리한 경우입니다.
- **역순 입력**: 삽입 정렬의 최악(O(n²))입니다. 5,000개에서 1.4초로, 같은 크기의 병합 정렬보다 약 180배 느립니다.
- **동률이 많은 입력**(few-unique): 퀵 정렬이 가장 빠릅니다. 3-way 분할이 같은 값 구간을 한 번에 확정하기 때문입니다. 작성자 기준 정렬이 이런 데이터입니다.
- **안정성**: 병합·삽입은 같은 키의 원래 순서를 유지하고, 퀵·힙은 깨뜨립니다. 그래서 LOG 정렬 기본값은 병합 정렬입니다.

### 측정으로 찾은 문제: 퀵 정렬 피벗

처음 구현은 처음·중간·끝 위치의 중앙값을 피벗으로 썼습니다. 이 방식과 3-way 분할을 함께 쓰면, 분할이 오른쪽 구간을 "두 번째로 작은 값이 맨 앞, 가장 작은 값이 맨 뒤"인 배치로 바꿔 놓아 다음 단계의 중앙값이 거의 최솟값이 됩니다. 그 결과 정렬된 2만 개 입력에서 비교 횟수가 **약 308만 번**(무작위 입력 43만 번의 7배), 실행 시간 268ms까지 늘었습니다. 무작위 위치 세 개의 중앙값으로 바꾸고 시드를 고정하자 비교 횟수 **46만 번**, 실행 시간 54ms로 돌아왔습니다.

## 2. 커밋 수 증가에 따른 연산 비용

```bash
python scripts/benchmark_repo.py          # 1,000 / 10,000 / 100,000 커밋
```

브랜치 10개를 오가며 커밋하고 가끔 merge 하는 DAG를 만들어 측정했습니다.

### 개선 전 (MERGE 조상 판정이 조상 전체를 BFS)

| commits | COMMIT/s | LOG ms | SORT author ms | PATH len | PATH ms | ancestors | ANCESTORS ms | hits | SEARCH(index) ms | SEARCH(scan) ms | prefix resolve ms |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 74,075 | 2.5 | 3.6 | 140 | 0.6 | 355 | 0.1 | 188 | 0.06 | 1.9 | 0.04 |
| 10,000 | 26,173 | 31.2 | 50.0 | 526 | 7.3 | 7,992 | 4.6 | 1,997 | 0.5 | 18.9 | 0.48 |
| 100,000 | 1,880 | 369.0 | 695.4 | 3,389 | 175.4 | 99,630 | 166.3 | 19,569 | 5.73 | 170.7 | 4.92 |

10배씩 늘 때 COMMIT/s가 74,075 → 26,173 → **1,880**으로 급격히 떨어졌습니다. 프로파일링(`cProfile`) 결과 실행 시간의 88%가 MERGE의 `is_ancestor` BFS였습니다. merge할 때마다 HEAD의 조상 전체(최대 N개)를 훑으니, merge가 일정 비율로 섞이면 전체 비용이 O(N²)이 됩니다.

### 개선 후 (조기 종료 + generation number 가지치기)

| commits | COMMIT/s | LOG ms | SORT author ms | PATH len | PATH ms | ancestors | ANCESTORS ms | hits | SEARCH(index) ms | SEARCH(scan) ms | prefix resolve ms |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 1,000 | 72,289 | 2.3 | 3.7 | 140 | 0.6 | 355 | 0.1 | 188 | 0.06 | 1.7 | 0.03 |
| 10,000 | 65,353 | 31.7 | 52.2 | 526 | 8.9 | 7,992 | 5.3 | 1,997 | 0.74 | 18.5 | 0.32 |
| 100,000 | 57,241 | 381.3 | 661.3 | 3,389 | 132.1 | 99,630 | 147.1 | 19,569 | 5.56 | 171.8 | 4.95 |

| 지표 | 1천 → 10만 (100배) | 판단 |
| --- | --- | --- |
| COMMIT/s | 72,289 → 57,241 | 개선 후 거의 일정 (개선 전 1,880) |
| LOG (위상 정렬) | 2.3 → 381 ms (약 166배) | O((V+E) log V) — 출력 자체가 N줄이라 줄일 수 없는 비용 |
| SORT author | 3.7 → 661 ms | O(n log n) 병합 정렬 |
| PATH / ANCESTORS | 0.6 → 132 ms / 0.1 → 147 ms | O(V+E). 조상 99,630개를 모두 방문 |
| SEARCH 역색인 | 0.06 → 5.6 ms | 결과 개수(k)에 비례. 같은 조건 순회 검색은 171.8 ms (약 31배 차이) |
| 축약 hash 해석 | 0.03 → 4.95 ms | 모든 hash를 훑는 O(N) — 다음 개선 후보 |

이 결과는 [`checklist.md` 4-1](checklist.md#4-1-커밋-수가-10배-늘면-병목은-어디이고-어떻게-개선하는가) 답변의 근거입니다.
