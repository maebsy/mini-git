## 항목 2. 구조 설계

### 2-1. 커밋 저장소 / 브랜치 / HEAD / 사용자 정보를 어떤 구조로 분리했고 각 책임은 무엇인가

📂 `mini_git/repository.py` (모듈 docstring에 표로 정리)

**답변.** `Repository` 안에서 상태를 역할별 필드로 나눴습니다.

| 필드 | 구조 | 책임 |
| --- | --- | --- |
| `commits` | `dict[hash → Commit]` | 커밋 데이터의 유일한 저장소. 불변 객체 |
| `children` | `dict[hash → list]` | 부모→자식 역방향 간선 (Commit에는 부모만 있으므로) |
| `branches` | `dict[이름 → hash]` | 브랜치는 "커밋을 가리키는 이름표"일 뿐 커밋을 소유하지 않음 |
| `head` | 브랜치 이름 | "지금 어느 브랜치 위에 있는가" |
| `user` | 문자열 | 다음 커밋의 작성자 |
| `index` | `InvertedIndex` | 검색 전용 파생 데이터 |

HEAD가 커밋이 아니라 **브랜치 이름**을 가리키는 것이 핵심입니다. COMMIT은 `branches[head]`만 새 커밋으로 옮기고, SWITCH는 `head`만 바꿉니다. 커밋은 `frozen=True` 데이터클래스라서 브랜치 이동이 커밋 내용을 바꿀 수 없습니다. 알고리즘은 `graph.py`/`sorting.py`로 분리해 저장소는 상태 관리에만 집중합니다.

### 2-2. 커밋 hash로 빠르게 조회하는 키-값 구조, 중복/충돌 방지

📂 `Repository.commits`, `mini_git/hashing.py` · 🧪 `HashTest` (모드별 500개 유일성, 강제 충돌)

**답변.** `commits`는 hash를 키로 하는 딕셔너리(해시맵)라 평균 O(1)로 조회합니다. 사용자가 축약 hash(4자 이상)나 브랜치 이름을 넣어도 `resolve()`가 전체 hash로 바꾼 뒤 조회합니다.

중복 방지는 생성기가 맡습니다. `HashGenerator.generate()`는 "이 hash가 저장소에 이미 있나?" 콜백을 받아 후보를 검사하고, 충돌하면 hash를 한 글자씩 늘립니다(7자 → 8자 …). 40자까지 충돌하면 순번을 섞어 다시 계산합니다. `counter` 모드는 순번 자체가 유일해서 원리적으로 충돌하지 않고, `sha1` 모드는 순번이 입력에 포함돼 같은 메시지를 반복 커밋해도 서로 다른 hash가 나옵니다.

### 2-3. 역색인(author/keyword)을 언제, 어떤 방식으로 갱신하는가

📂 `Repository._new_commit` → `InvertedIndex.add` · 🧪 `test_index.py`, `MergeTest`(merge 커밋도 검색됨)

**답변.** **커밋을 저장하는 바로 그 함수**(`_new_commit`) 안에서, 저장·간선 연결·브랜치 이동 직후에 갱신합니다. COMMIT과 MERGE가 모두 이 함수를 거치므로 어떤 경로로 커밋이 생겨도 색인이 빠지지 않습니다.

1. 메시지를 공백으로 split → lower → 앞뒤 문장부호 제거 → 메시지 안 중복 제거
2. 각 토큰의 posting 목록 끝에 hash 추가 (`by_keyword[token].append(hash)`)
3. 작성자 이름 정규화(공백 정리 + casefold) 후 `by_author[name].append(hash)`

항상 끝에 추가하므로 posting은 자동으로 생성순이고, 검색 결과를 따로 정렬할 필요가 없습니다.

### 2-4. LOG, PATH, ANCESTORS의 그래프 탐색 로직을 어떻게 재사용 가능하게 구성했는가

📂 `mini_git/graph.py`

**답변.** 그래프 함수는 저장소 클래스를 모르고 **"이 노드의 이웃은 누구인가"를 알려주는 함수**를 인자로 받습니다. 저장소는 세 가지 이웃 함수를 제공합니다.

| 이웃 함수 | 반환 | 사용처 |
| --- | --- | --- |
| `parents_of(h)` | 부모 | ANCESTORS, MERGE 판정, 위상 정렬의 진입 차수 |
| `children_of(h)` | 자식 | 위상 정렬에서 다음 후보 찾기 |
| `neighbors_of(h)` | 부모 + 자식 | PATH (무방향) |

그래서 BFS 하나(`bfs_distances`)를 ANCESTORS(부모 방향), PATH(무방향), MERGE(부모 방향)가 함께 씁니다. 간선 정의를 바꾸고 싶으면 넘기는 함수만 바꾸면 됩니다(4-2 참고). 테스트에서는 딕셔너리로 만든 가짜 그래프의 `__getitem__`을 그대로 넘깁니다.

### 2-5. docstring/주석 작성 기준

🧪 `test_constraints.py::test_public_api_has_docstrings` (공개 함수·클래스에 docstring이 없으면 실패)

**답변.** 세 가지 기준을 지켰습니다.

1. **모든 모듈 첫머리**: 이 모듈이 무엇을 책임지고 무엇을 모르는지, 핵심 개념(예: `index.py`는 순회 검색과 역색인 비용 비교표)
2. **공개 함수·클래스**: 무엇을 반환하는지보다 **왜 이 방법인지**를 씁니다. 예) `shortest_path`는 greedy가 사전순 최소를 보장하는 이유, `merge_sort`는 `<=`가 아니라 "오른쪽이 엄격히 작을 때만" 고르는 이유(안정성)
3. **주석은 코드만 보고 알 수 없는 것만**: 복잡도, 불변식, 함정(예: 퀵 정렬 피벗을 무작위 위치에서 고르는 이유)

## 항목 3. 동작 원리

### 3-1. 커밋 그래프가 왜 DAG여야 하고, 사이클이 생기면 어떤 문제가 생기는가

**답변.** 커밋은 "이전 상태(부모)에 변경을 더한 새 상태"입니다. 부모는 항상 자식보다 먼저 존재하므로 간선은 늘 과거를 가리키고, 그래서 방향이 있고(Directed) 되돌아오는 경로가 없습니다(Acyclic).

사이클이 생기면 (예: A의 부모가 B, B의 부모가 A)

- **순서가 정의되지 않습니다.** "부모가 먼저"인 LOG를 만들 수 없습니다. A를 먼저 내려면 B가 먼저여야 하고, B를 먼저 내려면 A가 먼저여야 합니다. Kahn 알고리즘에서는 두 커밋의 진입 차수가 영원히 0이 되지 않아 출력되지 않습니다.
- **조상 탐색이 끝나지 않습니다.** 방문 표시가 없으면 무한 루프, 있어도 "A는 A의 조상"이라는 모순이 생깁니다.
- **merge 판정이 깨집니다.** "대상이 이미 조상이면 merge 불필요"라는 판단이 의미를 잃습니다.

이 구현에서 DAG가 보장되는 이유는 새 커밋의 부모가 **이미 존재하는 커밋**만 될 수 있고, 커밋이 불변이라 나중에 부모를 바꿀 수 없기 때문입니다. 간선은 항상 생성 순번이 줄어드는 방향이라 출발점으로 돌아올 수 없습니다. 그래도 위상 정렬이 출력 개수를 검사해 사이클이 있으면 `CycleError`를 던지고, 테스트에서 일부러 사이클 그래프를 넣어 확인합니다.

### 3-2. LOG의 "부모가 먼저"를 위해 적용한 접근 (위상 정렬)

📂 `graph.topological_order` · 🧪 `TopologicalOrderTest`

**답변.** **Kahn 알고리즘**입니다.

1. 각 커밋의 진입 차수 = 부모 수. 부모가 없는 루트를 "출력 가능" 집합에 넣습니다.
2. 출력 가능 집합에서 하나를 꺼내 출력합니다.
3. 그 커밋의 자식들의 진입 차수를 1씩 줄이고, 0이 된 자식(=부모를 전부 출력한 자식)을 집합에 넣습니다.
4. 집합이 빌 때까지 반복합니다.

"부모를 전부 출력해야만 출력 가능"하므로 부모가 항상 먼저입니다. 출력 가능한 커밋이 여러 개일 때는 **우선순위 큐**(직접 구현한 최소 힙)에서 (timestamp, seq)가 가장 작은 것, 즉 가장 오래된 커밋을 먼저 꺼냅니다. 그래서 결과가 시간 흐름에도 맞고 실행할 때마다 같습니다. 비용은 O((V+E) log V)입니다.

단순히 "최신순 나열"이 아닌 이유는 브랜치가 갈라지면 시각 순서와 부모-자식 순서가 다를 수 있기 때문입니다. 위상 정렬은 시각이 꼬여 있어도(예: 시계가 틀린 기기에서 만든 커밋) 부모 우선 순서를 보장합니다.

### 3-3. PATH에서 최단 경로 알고리즘(BFS)을 고른 이유와 간선을 무방향으로 정의한 이유

📂 `graph.shortest_path` · 🧪 `ShortestPathTest`

**답변.**

**BFS를 고른 이유**: 최단 경로의 기준이 "간선 수"이고 모든 간선의 가중치가 1입니다. BFS는 거리 0, 1, 2 … 순서로 한 겹씩 넓혀가므로 처음 도달한 순간이 곧 최단 거리이고, O(V+E)입니다. 가중치가 다를 때 쓰는 다익스트라는 우선순위 큐 비용만 더해질 뿐 필요 없습니다.

**동률 처리**: target에서 BFS로 모든 노드의 "남은 거리"를 구한 뒤, source에서 출발해 남은 거리가 1 줄어드는 이웃 중 **hash가 사전순으로 가장 작은 것**을 고릅니다. 후보 경로 문자열은 처음 갈라지는 지점에서 비교가 결정되므로, 매 지점에서 가장 작은 hash를 고르면 전체 문자열도 가장 작습니다. 모든 최단 경로를 나열하는 정답지와 무작위 그래프 80개로 비교했습니다.

**무방향으로 정의한 이유**: 방향(자식→부모)만 허용하면 두 커밋 중 하나가 다른 하나의 조상일 때만 경로가 생깁니다. `feature`의 커밋과 `main`의 커밋처럼 형제 관계는 서로 조상이 아니라 항상 "No path"가 됩니다. 무방향으로 보면 공통 조상을 거쳐 연결되므로 "두 커밋이 얼마나 떨어져 있는가(갈라진 지점까지 몇 단계인가)"를 잴 수 있습니다. 예) `path 0000005 0000002` = `0000005 → 0000003 → 0000002`는 hotfix 커밋에서 위로 올라갔다가 main 쪽으로 내려오는 경로입니다.

### 3-4. 정렬 알고리즘의 평균/최악 시간복잡도와 안정 정렬 여부

📂 `mini_git/sorting.py` · 🧪 `test_sorting.py::StabilityTest` · ▶️ `python scripts/benchmark_sort.py`

**답변.**

| 알고리즘 | 평균 | 최악 | 안정 | 이유 |
| --- | --- | --- | --- | --- |
| **병합 (기본)** | O(n log n) | O(n log n) | ✅ | 항상 절반씩 나눔. 병합할 때 키가 같으면 왼쪽 먼저 |
| 퀵 | O(n log n) | O(n²) | ❌ | 피벗이 계속 한쪽 끝이면 n단계 분할. 분할 중 교환으로 원래 순서가 섞임 |
| 힙 | O(n log n) | O(n log n) | ❌ | 루트를 끝으로 보내는 교환이 같은 키의 순서를 섞음 |
| 삽입 | O(n²) | O(n²) | ✅ | 엄격히 작을 때만 앞으로 이동. 이미 정렬돼 있으면 O(n) |

**안정 정렬**은 키가 같은 원소의 원래 순서를 유지하는 정렬입니다. `LOG --sort-by=author`에서 시간순 목록을 작성자 기준으로 안정 정렬하면 같은 작성자 안에서 시간 순서가 그대로 남습니다. 그래서 기본 알고리즘을 병합 정렬로 했습니다. 테스트는 키 0~5인 300개 원소를 정렬해 병합·삽입은 순서 유지, 퀵·힙은 순서가 깨지는 것을 확인합니다.

### 3-5. 역색인이 순회 검색보다 빠른 이유 (자료구조/시간복잡도)

📂 `mini_git/index.py` · ▶️ `python scripts/benchmark_repo.py`

**답변.** 순회 검색은 질문이 올 때마다 **모든 커밋 메시지를 토큰으로 쪼개 비교**합니다. 커밋 N개, 메시지 평균 길이 L이면 O(N × L)입니다.

역색인은 이 작업을 **커밋할 때 미리** 해 둡니다. "단어 → 그 단어가 있는 커밋 목록"을 해시맵에 저장하므로, 검색은 해시맵 조회 O(1) + 결과 k개 출력 O(k)입니다. 결과와 무관한 커밋은 한 번도 보지 않습니다. 대가는 커밋마다 O(토큰 수)의 색인 갱신과 posting 메모리입니다. 보통 검색이 커밋보다 훨씬 자주 일어나므로 유리합니다.

실측(10만 커밋, `login` 검색, 결과 19,569건): 순회 171.8ms vs 역색인 5.6ms로 약 31배 빠릅니다. 결과가 적은 단어일수록 차이가 더 커집니다.

## 항목 4. 확장 질문

### 4-1. 커밋 수가 10배 늘면 병목은 어디이고 어떻게 개선하는가

근거: [`benchmark.md`](benchmark.md) 2절

**답변.** 실제로 측정해 보니 **MERGE의 조상 판정**이 가장 먼저 무너졌습니다. 처음 구현은 HEAD의 조상 전체를 BFS했는데, 커밋이 1천 → 10만으로 늘자 COMMIT/merge 처리량이 초당 74,075건 → 1,880건으로 떨어졌고, 프로파일링에서 실행 시간의 88%가 이 BFS였습니다. **조기 종료 + generation number 가지치기**(generation이 대상보다 작은 커밋 아래로는 내려가지 않음, Git commit-graph 방식)를 적용해 초당 57,241건으로 약 30배 개선했습니다.

남은 병목과 개선 방향:

| 지점 | 현재 | 10배 늘면 | 개선 |
| --- | --- | --- | --- |
| 축약 hash 해석 | 모든 hash를 훑는 O(N) | 10배 느려짐 | hash를 정렬해 이진 탐색(O(log N)) 또는 트라이(prefix tree) |
| LOG / 정렬 | O(N log N), 전체 출력 | 출력량 자체가 10배 | 페이지 단위 출력(`--limit`), 위상 순서 캐시 |
| ANCESTORS / PATH | O(V+E) 전체 탐색 | 10배 | generation으로 탐색 범위 제한, 양방향 BFS(PATH) |
| SEARCH | O(1) + O(k) | 결과 개수만큼만 | 결과 상위 N개만 반환, 자주 나오는 단어는 불용어 처리 |
| 메모리 | 커밋·색인 전부 메모리 | 10배 | 파일 영속화 + 필요할 때만 로드 |

### 4-2. PATH의 간선을 "부모 방향만 허용"으로 바꾸면 결과와 구현은 어떻게 달라지는가

**답변.**

**결과**: 경로는 자식에서 조상으로 올라가는 방향으로만 존재합니다.

| 질문 | 무방향 (현재) | 부모 방향만 |
| --- | --- | --- |
| `path 자식 조상` | 경로 있음 | 경로 있음 (같은 경로) |
| `path 조상 자식` | 경로 있음 | **No path** (거꾸로 갈 수 없음) |
| `path 형제A 형제B` | 공통 조상을 거쳐 경로 있음 | **No path** |

즉 "A가 B의 조상인가 + 몇 세대 위인가"를 묻는 기능이 되고, PATH(a, b)와 PATH(b, a)의 결과가 달라집니다(비대칭).

**구현**: `graph.shortest_path`는 이웃 함수를 받으므로 알고리즘 코드는 바꾸지 않습니다. 다만 현재 구현은 target에서 거꾸로 BFS해 "target까지 남은 거리"를 구하므로, 방향이 있으면 **역방향 이웃**을 넘겨야 합니다.

```python
# 무방향 (현재)
graph.shortest_path(a, b, repo.neighbors_of)

# 부모 방향만: source→target 이 '부모 방향'이므로,
# target 에서 거꾸로 탐색할 때는 '자식 방향' 이웃을 써야 한다.
remaining = graph.bfs_distances(b, repo.children_of)     # 1) b 에서 자식 방향 BFS
# 2) a 에서 출발해 parents_of 중 remaining 이 1 작은 부모를 고른다 (greedy 동일)
```

`shortest_path`에 "앞으로 갈 이웃"과 "거꾸로 잴 이웃"을 따로 받는 인자를 추가하면 두 정의를 한 함수로 지원할 수 있습니다. 경로가 있는지만 빨리 알고 싶으면 MERGE에서 쓰는 generation 가지치기도 그대로 적용됩니다.

### 4-3. LOG --sort-by=author가 "부모-자식 선후도 유지"로 강화되면 어떻게 해결하는가

▶️ `log --sort-by=author --topo` (이미 구현) · 🧪 `test_author_topo_keeps_parent_first`

**답변.** 두 조건이 충돌할 수 있습니다. 예를 들어 Carol의 루트 커밋은 작성자순으로는 맨 뒤지만, 모든 커밋의 조상이라 맨 앞이어야 합니다. 이때는 **부모-자식 순서를 절대 규칙으로, 작성자순을 2차 기준으로** 두는 것이 맞습니다.

해결책은 **우선순위 위상 정렬**입니다. Kahn 알고리즘에서 "출력 가능한 커밋" 중 무엇을 먼저 꺼낼지 고를 때, 우선순위 큐의 기준을 (timestamp) 대신 (작성자, timestamp, seq)로 바꿉니다.

- 부모를 모두 출력한 커밋만 후보가 되므로 부모 우선은 항상 지켜집니다.
- 후보가 여러 개면 작성자순이 빠른 것부터 나오므로 제약 안에서 최대한 작성자순에 가까워집니다.

이미 `log --sort-by=author --topo` 옵션으로 구현했고, 같은 `topological_order` 함수에 우선순위 함수만 바꿔 넘깁니다. 단순히 "작성자로 정렬한 뒤 위반을 고치는" 방식은 고칠 때마다 다른 위반이 생길 수 있어 위상 정렬 자체에 기준을 넣는 쪽이 정확하고 O((V+E) log V)로 효율적입니다.

### 4-4. hash 생성 방식을 카운터 ↔ 난수로 바꿀 때 테스트/재현성/디버깅에 미치는 영향

▶️ `--hash-mode counter|sha1|random`, `--seed` · 🧪 `HashTest`

**답변.** 세 방식을 모두 구현해 직접 비교할 수 있게 했습니다.

| 관점 | 카운터 (`0000001`) | 난수 | 난수 + 시드 고정 |
| --- | --- | --- | --- |
| **테스트** | 기대값에 hash를 그대로 적을 수 있음 (`assertEqual(out, "[main 0000001] ...")`) | hash를 정규식이나 실행 결과에서 꺼내 써야 함 | 카운터처럼 고정값 사용 가능 |
| **재현성** | 같은 명령 순서면 항상 같은 hash | 실행마다 다름 → 버그 재현 시 hash가 바뀜 | 같은 시드면 같음 |
| **디버깅** | hash만 보고 생성 순서를 앎. 로그를 읽기 쉬움 | 순서 정보가 없음 | 순서 정보는 없지만 재현 가능 |
| **PATH 동률 처리** | 사전순 = 생성순이라 "먼저 만든 경로"가 선택됨 | 동률 결과가 실행마다 달라질 수 있음 | 시드별로 고정 |
| **유일성** | 순번이 유일하므로 원리적으로 충돌 없음 | 충돌 가능 → 검사·확장 로직 필수 | 동일 |
| **실제 Git과의 유사성** | 낮음 | 높음 (예측 불가) | — |

그래서 테스트와 문서 예시는 카운터 모드(`--hash-mode counter`)와 가짜 시계로 실행해 결과를 고정하고, 기본 실행은 실제 Git처럼 내용 기반 `sha1`을 씁니다. 난수 모드를 테스트에 쓸 때는 반드시 시드를 고정하고(`--seed 42`), 같은 시드가 같은 결과를 내는지 테스트로 확인합니다(`test_random_mode_reproducible_with_seed`).
